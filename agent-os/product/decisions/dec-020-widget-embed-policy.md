# DEC-020: The Widget Embed Policy Follows the Calendar's Allowed Domain

> Date: 2026-09-23
> Status: Accepted
> Category: Technical
> Stakeholders: Tech Lead, Calendar Owners

## Decision

Where a calendar's widget may be framed is **the calendar owner's decision**, and it is enforced by the visitor's browser through a per-calendar `Content-Security-Policy: frame-ancestors` header on the widget HTML shell (`/widget/<calendarName>/...`). The universal `frame-ancestors *` that the shell previously sent is retired. Six rules bound the policy; the implementation is PR #639.

**1. The shell's framing policy is the enforcement point.** The owner's **Allowed Domain** setting is enforced where the browser decides whether to render the frame — the shell's `frame-ancestors` — and not only at the widget data API. The data API's Origin check never sees the embedding page in the standard embed: the widget iframe is served from the instance, so its own data calls are same-origin, carry `Sec-Fetch-Site: same-origin`, and skip Origin validation by design. A control enforced only there restricts nothing an owner would recognize as embedding. `X-Frame-Options: DENY`, set globally by helmet, is removed on widget routes because in legacy browsers it would override `frame-ancestors` and block every embed.

**2. Policy shape.** `WidgetDomainService.frameAncestorsFor` builds the whole header value; `app_routes.ts` only sets it.

- Every policy permits `'self'` — the instance's own admin preview on the calendar's **Widget** tab.
- Every policy, in production included, permits `http://localhost:* http://127.0.0.1:* http://*.localhost:*`, the CSP counterpart of `isOriginAllowed`'s development exception. Those sources are reachable only by a page served from the visitor's own machine; the security audit of PR #639 accepted them as-is. (The IPv6 loopback that `isOriginAllowed` also accepts has no CSP host-source form and is absent.)
- A configured domain adds `https://<domain>:*` and `https://<www-twin>:*` — **https only**, any port unless the owner entered one, in which case that port is pinned.

**3. No configured domain means no embedding elsewhere.** An unconfigured calendar gets `'self'` plus the localhost sources, and nothing else. Embedding outside the instance is something an owner turns on by naming a site, not something they must remember to turn off. An unknown calendar name gets the same policy as an unconfigured calendar. That is uniformity, not a privacy property — a calendar's existence is already public through the site's 404 and the public API — and it is not to be cited as one. When the public interface is not yet bound, or the lookup throws, the shell fails closed to `frame-ancestors 'self'` alone.

**4. One matching rule, one place.** `WidgetDomainService.matchesAllowedDomain` is the host rule for both the shell policy and the widget API's Origin validation: case-insensitive; a trailing dot ignored; the entered host and its `www.` twin equivalent — `www.` is added to or stripped from whatever host the owner entered, so `events.example.com` also admits `www.events.example.com` (stripping `www.` never produces a bare TLD); every other subdomain a different site; a port significant only when the owner entered one. Saved domains are normalized — lowercased, trailing dot removed, the with- or without-`www.` form the owner typed kept. A calendar has **one** allowed domain; the storage, API and UI all carry a single value. The two surfaces share the host rule but **not** the scheme rule: Origin validation accepts an `http://` origin for a configured domain while the shell permits only `https://`. They can disagree on scheme, and nothing downstream may assume otherwise.

**5. Policies are cached for 60 seconds.** `FRAME_ANCESTORS_CACHE_TTL_MS` is 60 000. A domain change through `WidgetDomainService.setAllowedDomain` invalidates its own process's entry at once; another process serving the same instance picks the change up within the TTL. The cache is capped at 1 000 entries and cleared wholesale at the cap, because the shell answers any well-formed calendar name and unknown names are cached too. Owner-facing copy promises that a change reaches every embed within "up to a minute"; a TTL change must change that copy in the same commit.

**6. The header discloses the allowed domain — a bounded, deliberate exception.** A browser cannot enforce a policy it cannot read, so any anonymous `GET /widget/<calendarName>` returns the calendar's `widgetAllowedDomain` inside the CSP value. Elsewhere the field is deliberately withheld from anonymous callers: `toPublicCalendarObject` drops it from every public JSON projection. This exception is intrinsic to `frame-ancestors` enforcement and is bounded by it: the value appears only in that header, only on the widget shell route, and only in the form the browser needs. It does not license adding the field to any JSON projection, and no other calendar setting may ride along in a widget header. The disclosure is also small in substance — the domain names a website on which the owner is, by the setting's purpose, publicly showing the calendar. It is an owner-configuration disclosure, **not a [DEC-004](dec-004-privacy-first-public-access.md) matter**: no attendee or visitor data is involved.

The shell policy is not a funding surface. It reads the allowed domain only and never consults `FundingInterface`; the `widget_embedding` gate under [DEC-011](dec-011-federated-value-boundary.md) stays where it was, on the widget data endpoint and on setting the domain.

## Context

The **Allowed Domain** control has been in calendar settings since the widget shipped, and the admin UI presented it as the thing that decides where a calendar can be embedded. An audit on 2026-09-23 of a live calendar's embed found that it decided nothing for the standard iframe embed. The shell sent `frame-ancestors *` for every calendar, and the widget data API's Origin check — the only place the setting was consulted — is skipped for the iframe's own same-origin requests. Any site could paste any calendar's snippet and have it render.

`frame-ancestors *` was deliberate. Commit e42d61ad recorded its rationale in a "Security rationale" comment in `src/server/app_routes.ts`: the widget shows only public, read-only event data with no authenticated state, forms or state-changing actions, so clickjacking risk is negligible; the widget data API "independently enforces a per-calendar domain allowlist via Origin header validation"; and a narrowed header would need a database lookup on every widget page load, a complexity cost not justified for public-only content.

**This decision retires that reasoning as the operative policy, and does not merely add to it.** The old rationale answered a different question. Its clickjacking conclusion is still true on its own terms — the widget has nothing to hijack a click toward — but clickjacking was never what the Allowed Domain control is for. The control exists so that an owner decides which website their calendar appears inside; that is a question of placement and association, and "the content is public" does not answer it. Its load-bearing premise — that the data API's Origin check enforced the allowlist — was false for the embed as actually built. And its cost argument is met by the 60-second cache in rule 5. Because the old reasoning was only ever a code comment, never a numbered decision, this is not a supersession under the index conventions; it is a correction of a policy that had no decision record. The comment that replaced it in PR #639 cites this decision.

## Alternatives Considered

**Keep `frame-ancestors *` and fix enforcement at the data API.** Make the iframe's data calls carry something the API could check against the allowed domain. Rejected: inside the iframe, the only signals of the embedding page are client-side (`document.referrer`, `location.ancestorOrigins`), and the second is absent in Firefox. Whatever the iframe reports, it reports about itself; a check built on it is advisory. The browser's `frame-ancestors` evaluation is the only enforcement the embedding page cannot talk its way past.

**Unconfigured means open.** Keep `*` until an owner names a domain, then narrow. Rejected: it turns the control into an opt-in restriction that protects only owners who find the setting, while the UI had always described it as the gate. It would also leave every calendar that never configures a domain framable anywhere, which is the condition the audit found.

**Exact host match, no `www.` twin equivalence.** Rejected: owners type the apex and sites commonly serve on `www` (or the reverse), and the failure is silent — the owner sees their own site show a refused frame and reads it as breakage. Equivalence goes no further than `www`: a wildcard subdomain rule would admit every tenant of a shared hosting domain an owner happened to type.

**Several allowed domains per calendar.** Deferred, not rejected. The single-value model already runs through storage, API and UI, and `www.` twin equivalence covers the most common reason for a second entry. Partners who want the same events on their own site have the in-network route of running their own calendar and reposting.

**Drop the localhost sources in production.** Rejected by the PR #639 security audit: they are reachable only by a page on the visitor's own machine, they mirror the Origin check's existing exception, and they keep local development of an embedding site working against a real instance.

**No cache, a longer TTL, or cross-process invalidation.** No cache puts a database read on every load of a public, unauthenticated route. A longer TTL stretches the owner-visible delay after a change. Cross-process invalidation would need a bus for a setting that changes rarely. Sixty seconds bounds both the cost and the delay, and the delay is one owners can be told about in a sentence.

## Rationale

A setting an owner can see and change must do what it says; an inert security-looking control is worse than none, because it teaches owners they have a protection they do not. The placement question — which site a calendar appears inside — belongs to the calendar's owner, and the only reliable enforcement point for it is the browser's frame-ancestors check on the framed document. Defaulting to "no embedding elsewhere" makes the control's description true for every calendar, including the ones whose owners never open the **Widget** tab. Putting the host rule in one method keeps the shell and the API from drifting apart on the part that matters most to owners — which hosts count — and naming the scheme difference keeps anyone from relying on a sameness that is not there. The header disclosure is the unavoidable price of browser enforcement, and bounding it in writing stops it from becoming a precedent for loosening the public projections.

## Consequences

- **Deploy-time breakage is possible and intended.** A calendar whose stored domain does not match the site actually embedding it — a typo, or a site that moved — stops rendering there the moment this ships, where before it rendered regardless. Operators upgrading an instance with existing embeds should check stored domains against the sites in use before deploying.
- **Owners need to be told.** The **Widget** tab states the `www.` twin rule, the one-domain limit, the https requirement, that the restriction is browser-enforced, and that a change takes up to a minute; the embed section states that the snippet will not render on another site until a domain is set, without hiding the snippet. `docs/guides/calendar-owners/embed.md` carries the owner-facing explanation, including the website-builder case where the builder wraps pasted code in a frame of its own, which the browser also checks.
- **Reintroducing a broad policy is a decision change.** Sending `frame-ancestors *`, or any source not derived from the calendar's allowed domain, anywhere on the widget path requires amending this decision — not a code comment.
- **The public projection comment in `src/server/public/api/v1/calendar.ts`** now names this exception instead of calling the field operator-internal.
- **The widget's `postMessage(..., '*')` calls** in `src/widget/stores/widgetStore.ts` are unaffected: their payloads (frame height, in-widget path) carry nothing sensitive, and the frame they post to is now bounded by this policy anyway.
- **A future multi-domain model** changes rule 4's "one" and the owner-facing copy together; the matching rule and the policy builder already operate per domain and would iterate.
