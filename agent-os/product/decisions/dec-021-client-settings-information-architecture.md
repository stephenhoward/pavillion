# DEC-021: Client Settings Information Architecture

> Date: 2026-10-20
> Status: Accepted
> Category: Technical
> Stakeholders: Tech Lead, Development Team

## Decision

Everything under `/settings` in the client SPA is **one three-level navigation tree** — root (Calendar, Account, Instance for admins, Log out), section (one group's leaves), leaf (a routed page) — rendered from **one set of markup**. The viewport decides only where the tree is drawn: below `md` it is a drill-down of full pages with a back link and the bottom tab bar; at `md` and up the two list levels collapse into a persistent secondary sidebar beside the main nav and the leaf renders in the content column. Nine rules bound it.

**1. One tree, one markup.** One list component, `settings/nav-list.vue`, renders both the phone drill-down page (`settings/list-page.vue`) and the desktop sidebar group (`settings/tree.vue`). The parent sets a static `--page` / `--sidebar` modifier, and CSS keyed on that modifier and on `pav-media(md)` decides chevrons and placement. There is no second set of nav markup. At `md+` the tree is a sticky scroll container one viewport tall: its group list scrolls while Log out stays pinned to the tree bottom. Two invariants hold it: **`html` sets no `overflow`, and no element between `body` and the tree sets any** (either breaks `position: sticky`); `body`'s `overflow-x: hidden` in `base/_reset.scss` is allowed because, with `html` clear, it propagates to the viewport instead of creating a scroll container, and the padding of the scrolling group list must stay at or above the rows' focus-ring reach (2px outline plus 2px offset), because that list clips.

**2. One breakpoint, and the shell owns it.** The tree switches at the main-nav breakpoint, `md` (768px), the width at which the main nav moves from the bottom tab bar to the sidebar. Settings borrows it and declares no second one. The script constant is `SHELL_SIDEBAR_UP_PX` in `src/client/assets/breakpoints.ts`, pinned to `--pav-breakpoint-md` by `src/client/test/shell-breakpoint.test.ts`, and read through the `useShellLayout` singleton (`src/client/composables/useShellLayout.ts`). It is client-local, not in `src/common/ui/assets/breakpoints.ts`, because the client and public scales differ by app ([DEC-019](dec-019-shared-ui-module.md) rules 4 and 7). The breakpoint is **exclusive below**: a "below md" style rule uses `pav-media-down(md)` (at most 767px), never `(width <= 768px)`, which overlaps the md shell at exactly 768px. Older client components outside settings still carry `(max-width: 768px)` queries; they are tracked debt (pv-34km), not precedent. The tree width, `--pav-settings-tree-width: min(14rem, 30vw)`, is capped by the viewport so enlarged text never squeezes the content column hard enough to need a second breakpoint; wide leaves adapt with `@container` queries on the content column instead.

**3. The icon rail is a route opt-in that CSS applies.** At `md+` on any `/settings/*` route the main sidebar collapses to an icon rail. The route declares the need with `meta.shellRail` (set on the `/settings` record in `src/client/routes.ts`); `app-shell.vue` turns it into `.app-shell--rail`, and `_shell-nav.scss` applies it only inside `pav-media(md)` by swapping two custom properties, `--pav-shell-nav-width` and `--pav-shell-nav-padding`. Shell components read those properties rather than being overridden, because `_shell-nav.scss` sits in a cascade layer that any unlayered scoped rule beats. There is no script viewport branch for the rail, and nothing transitions. Rail links keep their accessible names through sr-only labels. `meta.shellRail` is a general shell opt-in; settings is its only user today.

**4. The calendar switcher lives in the detail pane, never in the tree.** The root list has one Calendar row, and the sidebar group heading is the static word "Calendar". The switcher sits in the page header (`settings/page-header.vue`): beside the section title on phone, in the eyebrow above the leaf title on desktop. Its sheet lists calendars only, never settings destinations. On a calendar leaf, switching keeps the viewer on the same leaf of the other calendar.

**5. Leaf visibility has one source.** `src/client/components/logged_in/settings/nav-items.ts` (`firstVisibleLeaf`, `isVisibleLeaf`) decides which leaves a viewer sees. It also holds the **action rows** that end a list, Log out on the root and Leave calendar on the calendar section of a calendar the viewer edits but does not own: buttons in the danger style, never leaves, so no index forwards to one, no guard reads one, and Leave calendar confirms in a dialog before it acts. The tree, the index forward, the list page's resize watch, the owner-only calendar gate and the funding-disabled redirect all read it, each through a context built once by `buildSettingsNavContext` in `src/client/service/settings-guards.ts` from the viewer's own loaded data. Hiding a leaf is a convenience, not access control: the server endpoints each leaf calls remain the enforcement point, consistent with [DEC-015](dec-015-activity-log-routing-keys.md) rule 3. `settings-guards.ts` (in `service/`) importing `nav-items.ts` (in `components/`) is the **one sanctioned service → components edge**: `nav-items.ts` is a presentation tree that also holds visibility, and it is not moved or split to avoid that edge.

**6. Index routes forward at md+, and that is the only viewport-dependent navigation in script.** `/settings`, `/settings/calendar/:calendar`, `/settings/account` and `/settings/admin` render their list page below `md` and forward to the group's first visible leaf at `md+`. One helper, `settingsIndexTarget`, computes the target; it has two call sites, the `settingsIndexRedirect` guard and `list-page.vue`'s resize watch (a post-commit `router.replace`). A calendar the viewer cannot resolve — not in their loaded list, or the load failed — never forwards, at either viewport, so non-member and nonexistent calendars stay non-disclosing. The boundary on other script that reads the shell breakpoint: it may **navigate** only through the index forward. Any other viewport watch may only **move focus** to the page h1, to recover focus from a container the viewport just hid. Today the allowed non-navigation readers of `useShellLayout` are the tree (`tree.vue`, crossing below md with focus in the tree) and the list page (`list-page.vue`, crossing up with focus in the page), plus `settings/root.vue`'s page-mode focus rule. The rail is not a reader (rule 3). pv-ms7c is the consolidation point for viewport-toggled focus and header controls.

*Corollary:* **every settings URL emitted outside the SPA addresses a leaf, never an index.** That covers the server's emails (`src/server/common/helper/settings-links.ts`: `calendarReportsPath` → `calendar_reports` and `adminModerationReportPath` → `moderation_report_detail` for the moderation emails, `adminAccountsPath` → `accounts` for the admin application notice, path only, origin from `publicUrl`), both Stripe return paths (the checkout return in `FundingForm.vue` → `calendar_general`, or `funding_plan` without a calendar; the billing-portal return, which the client does not yet send (pv-vhyu), → `funding_plan` at `/settings/account/funding`, never `/settings/account`), and notification targets (`src/client/service/notification-target.ts` → `calendar_widget` for editor invitations, the first leaf an editor sees because Editors is owner-only, `calendar_report_detail` for owner reports, `moderation_report_detail` for admin reports). An index URL arriving from outside would land on a different leaf depending on the reader's viewport.

*Focus corollary:* in page mode only, `settings/root.vue` moves focus to the h1 after a path change. It skips a calendar-only change (the switcher restores its own focus) and `calendar_report_detail`, the one leaf that owns its focus; other `reportId` destinations are not skipped. History traversal (Back/Forward) is a path change and moves focus on purpose. Nothing moves at `md+` or on initial load.

**7. Every settings destination is a routed leaf; no tab or query navigation under `/settings`.** A leaf may own sub-routes that keep its tree row current: `calendar_report_detail` (`reports/:reportId`) under Reports, and `moderation_report_detail`, `moderation_settings` and `blocked_instances` under Moderation. `findLeafByRouteName` and `isVisibleLeaf` resolve a sub-route to its owning row. `blocked_instances` is linked from the Federation page but belongs to Moderation. In-page tab state that **never reaches the URL** is permitted inside a leaf's own content; today it exists in the admin Accounts (`admin/accounts.vue`) and Funding (`admin/funding.vue`) pages and in the calendar Import leaf's URL / file tabs (`calendar-management/import-sources/AddImportSourceForm.vue`). A tab or query parameter that selects a settings destination is not permitted; the only `?tab=` handling is the temporary redirect in rule 9.

**8. A guard redirect never adds a history entry.** It inherits the navigation's push or replace, and replaces only when the URL being redirected away from is already in the address bar (Back/Forward, a first load), so it neither adds an entry nor erases the page the viewer came from. `withHistoryMode` in `settings-guards.ts` is the one form every settings guard uses. Post-commit `router.replace` calls (the list page's resize forward and the calendar pane's ownership watch) replace unconditionally. Every redirect target is a fixed named route; its params come only from the matched path params or a validated value (a UUID-v4 report id), and no query value is carried unvalidated.

**9. The legacy `?tab=reports` redirect is temporary.** `legacyTabReportsRedirect` is a `beforeEnter` entry on the `calendar_management` index record, after `mustBeLoggedIn` and before the index forward, so it runs at both viewports and the record's own guards still run. It maps only `tab=reports` onto `calendar_reports`, plus a single UUID-v4 `report` value onto `calendar_report_detail`, because moderation emails sent before rule 6 hold that form. No other query key is carried and other `?tab=` values are ignored, so the index behaviour applies. It is removed one release after the email change (pv-y5xy).

## Context

Before this decision the settings area had three navigation paradigms: calendar management used local tab state with a `?tab=` query, instance admin used routed pages behind its own nav strip, and the account page was one long scroll with sections. The page heading doubled as a switcher between them. None shared markup, and none was the phone drill-down the mockup called for.

The rules produced the current shape: Account is three leaves (Profile, Security, and Funding Plan, listed only when the instance has funding enabled); calendar report detail is the path `reports/:reportId`, mirroring admin's `moderation/reports/:reportId`; every settings record carries its own `mustBeLoggedIn` or `mustBeAdmin`, because a parent's `beforeEnter` does not run between siblings; every icon is a Lucide component.

All the routes sit under the client's already-reserved `settings` segment, so [DEC-018](dec-018-root-calendar-urls.md) needs nothing reserved and `SERVER_OWNED_SEGMENTS` is unchanged. The server-built settings paths live in `src/server/common/helper/` rather than `src/common/routing`, because they are client SPA paths that only server emails emit, not public page shapes; they sit in the server's shared helpers rather than in one domain because more than one domain emits them (moderation and accounts), and [DEC-003](dec-003-domain-driven-architecture.md) forbids either importing the other.

## Alternatives Considered

- **Separate phone and desktop nav markup.** Rejected: two renderers drift on rows, labels, visibility and current-item state. One component with a static modifier keeps every row identical in both placements.
- **A second, settings-only breakpoint.** Rejected: the tree and the main nav would switch at different widths, producing a band where the shell is a sidebar and settings is still a drill-down (or the reverse). Capping the tree width (rule 2) answers the enlarged-text case that motivated it.
- **A script viewport branch for the rail.** Rejected: CSS already knows the width, and a script branch adds a frame where script and stylesheet disagree. The route says what it needs; the stylesheet says when.
- **A record-level `redirect:` for `?tab=`.** Rejected: a record redirect skips the record's own `beforeEnter`, so `mustBeLoggedIn` would not run. A guard entry keeps the guard order.
- **A permanent `?tab=` map, or carrying every `?tab=` value.** Rejected: only `tab=reports` exists in sent mail; mapping the rest would keep a query vocabulary alive that rule 7 retires, and carrying unvalidated query values into a redirect echoes URL input.
- **`?report=` query form for report detail.** Rejected for a path parameter, which mirrors the admin route, keeps the Reports row current through the sub-route, and needs no query allowlist.
- **Leaf title keys in route meta.** Rejected for lookup by route name in `nav-items.ts`, so a title is declared once, in the tree.

## Rationale

The viewport should change where navigation is drawn, never what it contains. One markup and one visibility source make "the tree shows X" and "the redirect allows X" the same statement, so they cannot disagree. Borrowing the shell breakpoint means one width decides every layout change, and the script constant is pinned to the Sass value by a test, not by convention. Confining viewport-dependent navigation to the index forward leaves one place where a URL means different things at different widths; the leaf-only corollary keeps every URL that leaves the SPA out of that place. The history rule keeps Back working the way a viewer expects across redirects. The temporary redirect pays for links already in inboxes without making `?tab=` a permanent contract.

## Consequences

- **Adding or moving a settings page** means a route record with its own guard, an entry in `nav-items.ts` (which gives it its title and visibility), and, if it is a sub-page, a `subRoutes` entry on its owning leaf. A destination selected by tab or query state is out of bounds (rule 7).
- **Emitting a settings link from the server or a provider** targets a leaf route (rule 6). The server's paths come from `src/server/common/helper/settings-links.ts`, one function per leaf, pinned on both sides by `src/server/common/test/helper/settings-links.test.ts` and `src/client/test/routing/settings-links-contract.test.ts`. A new server-emitted settings link adds a function there and a literal to both tests; no domain builds a settings path by hand.
- **Changing the shell breakpoint** changes the settings tree with it; `shell-breakpoint.test.ts` fails until the constant and the Sass value agree. At 768px with the rail (4rem) and the tree (14rem), the content column's content box is 26rem.
- **The current nav item** is marked the same way in every variant (main sidebar, rail, phone tabs, settings tree): `aria-current="page"`, the label's weight and active colour, and a 1px inset border in the active label colour (`--pav-nav-active-text`). The border is the item's one non-colour cue, so it takes the colour that reaches 3:1 against the surface in both themes. Forced-colours mode, which drops the border, keeps an outline.
- **Client-only tokens.** `--pav-settings-tree-width` and `--pav-shell-rail-width` are client tokens, outside the [DEC-019](dec-019-shared-ui-module.md) shared tier.
- **Removing the `?tab=` redirect** (pv-y5xy) deletes `legacyTabReportsRedirect` and its route entry; no other `?tab=` handling exists to remove.
- **Funding-plan placement.** Account → Funding Plan is the account-side home for a viewer's plan, and Instance → Funding is the admin's, in [DEC-007](dec-007-community-funding-model.md) vocabulary. Where a funding plan is started (pv-f7sz, today a calendar's Extended Features section) is decided against this tree: an entry point is a leaf or a control inside a leaf, never a tab or query state.
- **Accepted cost.** A Stripe checkout session created before rule 6 shipped returns to `?tab=settings&session_id=…`, which rule 9 does not map; at `md+` the index forward drops `session_id`. The plan is still recorded server-side and the Funding Plan page shows it.
