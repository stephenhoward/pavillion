# DEC-019: Shared Frontend UI Lives in `src/common/ui`

> Date: 2026-10-06
> Status: Accepted
> Category: Technical
> Stakeholders: Tech Lead

## Decision

Browser-side Vue components, composables and styling that more than one frontend app consumes live in one module, `src/common/ui/`. Its consumers are the public site (`src/site`), the embeddable widget (`src/widget`) and the authenticated client (`src/client`). `src/common/ui/README.md` is the module's working contract; this file records why it is shaped that way and which rules are load-bearing. Ten rules bound it. The tenth also reaches past the module, into the site's and widget's own style.

**1. Name and location: `ui`, under `src/common`.** The module is `src/common/ui`, not `src/shared/` and not `public-ui`. It sits beside the other `src/common` areas because it follows the same rule they do: code that more than one side of the tree imports. It is called `ui` rather than `public-ui` because the client is a full consumer (rule 4), not a future one.

**2. `src/common` has a browser-only part, and the server may not import it.** Nothing under `src/server/` imports `src/common/ui`; the module assumes a browser. This is the first *enforced* instance of a condition that already existed without a name: `src/common/i18n/cookie.ts` (reads `document.cookie`) and `src/common/utils/ics-generator.ts` are browser-oriented `src/common` files with no such rule over them. The rule is not retroactively broken by those files. It names a property they already had and enforces it for this module only.

**3. The boundary is an allowlist, enforced by `src/common/ui/test/boundary.test.ts`.** A module under `src/common/ui/` may import anything under `@/common/*`; the packages `vue`, `vue-router`, `luxon`, `i18next` and `i18next-vue`, and no other package; and Sass builtins in a style context. Its own tests under `src/common/ui/test/` get a separate, still closed list (`vitest`, `@vue/test-utils`, `fs`, `path`). It may never import `@/client`, `@/site`, `@/widget` or `@/server`, by alias or by a relative path that escapes into them, and may never reach outside `src/` by a relative path. The package list is closed rather than a denylist because the likely breach of a presentational module is not an `@/site/...` import, which a reviewer sees, but `pinia`, `axios` or an app store pulled in through one of them. Shared components take their data as props so that none of those is ever needed. The scan is textual (regex over source, comments included), not an AST walk. Moving it to the TypeScript AST is open work on pv-e62b.

**4. Styling is token-only, and the client is a full consumer.** A shared component reads `--pav-*` custom properties, and only the names in the shared tier of `src/common/ui/TOKENS.md`. It never reads a `$public-*` SCSS variable, never includes a `public-*` mixin other than the layout-only ones `boundary.test.ts` allowlists, and writes no dark-mode rule: no `[data-theme]` selector, no `prefers-color-scheme` query and no `color-scheme` declaration. Each token already switches under the mounting app's theme selector, and dark values are declared only in each app's token layer. A `$public-*` value is fixed at build time and cannot take on another app's theme. A `--pav-*` property resolves in the browser against whichever app mounts the component, so one compiled component renders in each app's own theme. TOKENS.md records two tiers. **Shared** names are declared by every app, and they are the only names a shared component may read. **Public-only** names are declared only by the site and widget token layer, for those apps' own components. The client does not declare them, so a shared component that read one would render unstyled there, and `boundary.test.ts` rejects that. Every app declares every shared name its own way: the site and widget through the `public-theme-tokens` mixin, the client through its theme layer. A name shared by all three apps does not imply a shared value. Each app keeps its own palette behind the name. Whether the site and widget should converge on the client's palette is open on pv-olnr. `components/EmptyState.vue`, mounted by the site's discovery page, the widget's list view and the client's feed, is the proof that the contract holds in all three apps. `boundary.test.ts` deliberately carries no "the client imports nothing from here" assertion. `test/public-theme-tokens.test.ts` fails if a shared name is missing from either app's token layer, if a public-only name is declared anywhere in the client's style tree, or if the site and widget token layer declares a name neither tier records.

**5. A shared component puts no text and no focus indicator on or in `--pav-accent`.** The accent is decoration (rules, rings, borders) and is never the only carrier of a state. The reason is that the widget's accent is owner-configurable (`widgetStore.injectAccentColor`) and TOKENS.md has no ink paired with it, so no text colour is guaranteed to contrast with it. `boundary.test.ts` checks token names, not pairings, so this rule is enforced by review. The gap and its owner is pv-8l49 (an accent/on-accent text pair, or a contrast guard on the owner's choice). When that lands, the rule relaxes to "text on the accent reads the paired on-accent token". One known instance leans on the accent harder than the rule wants: the today marker in `WeekView.vue` and `MonthView.vue` is an accent ring (about 2.25:1 against the light surface) plus `aria-current="date"` and a small weight difference. It satisfies the letter of the rule, since the ring is not the only carrier because `aria-current` is, but it is weak visually and is a candidate for fixing under pv-8l49.

Outside the module, the site's and widget's own components still put white text on the accent in a few places: `public-button-primary`, the selected filter pill, the active date filter and date pill, and the add-to-calendar hover. These are excluded from the token work on purpose. White is a single-theme value, and the right replacement is the on-accent ink that pv-8l49 / pv-jqa4 will define, not a token minted now. The theme guard (rule 10) does not report them. It also does not report its other two residuals: any colour literal written straight into a component, and a component-local SCSS colour variable. Both render identically in light and dark, so neither can be the light-value-in-dark-mode bug the guard exists to stop, but neither goes through the token layer. A warn-only rule for them is filed as pv-4wwt.

**6. A shared component owns its translation keys, in the `ui` namespace.** Apps register the bundle (`uiResources` from `src/common/ui/locales.ts`, spread into each app's static i18next `resources`) and never define or override a `ui` key. This keeps a component's copy identical wherever it is mounted, and means no app has to know which keys its dependencies read. When a string moves from an app view into a shared component, its key moves into `ui`. The bundles live today at `src/common/ui/calendar-views/locales/{lang}/ui.json` because calendar views are the only shared feature with copy. The first other shared feature that needs keys moves the bundles up to `src/common/ui/locales/{lang}/ui.json` and adds its keys to that single per-language file. It does not add a second file per language: `ui` is one namespace, and `locales.ts` maps one file to it per language. `test/locales.test.ts` fails if a language in `AVAILABLE_LANGUAGES` lacks a bundle or its keys differ from English.

**7. Placement inside the module.** `composables/` holds composables useful across features (`useLocale`, `useLocalizedContent`, `useContainerWidth`). A composable that only makes sense with one feature's state lives in that feature's folder, next to the components it serves (`calendar-views/useCalendarViewState.ts`, `useCalendarWindowSync.ts`, `useCalendarViewContainer.ts`). Breakpoints a component must branch on in script are two literals in `assets/breakpoints.ts` that mirror the `public-tablet-up` and `public-desktop-up` mixins. Sass and TypeScript cannot share one declaration, so `test/breakpoints.test.ts` parses the mixins and fails when the two drift. The Creato Display font files live in `assets/fonts/`, with their `@font-face` rules in `assets/fonts.scss`, which every app's global stylesheet loads, so the faces are declared once. `assets/mixins.scss` is the permanent home of the site's and widget's design system. It holds three things. First, the non-colour `$public-*` constants: type, spacing, radius, motion and layout breakpoints, which rule 10 keeps compile-time. Second, the `public-*` component mixins, all of which take colour from runtime tokens. Third, the token layer itself, `public-theme-tokens` and its private `_public-theme-dark-values` helper. It is not legacy surface awaiting retirement. Site and widget style loads it directly as `@use '@/common/ui/assets/mixins'`. It is still not for the client, and a shared component may use only the layout-only mixins `boundary.test.ts` allowlists. The block of unprefixed aliases inside it is compatibility surface for call sites that predate the `public-*` names, and it is not part of the design system: `filter-*`, `search-*`, `input-base`, `mobile-only`, `medium-size-device`, the `$spacing-*` scale and `$font-regular` / `$font-medium`. Its one remaining consumer is `search-filter-public.vue`. Retiring the block, together with the uncalled constants and the `public-wide-up` mixin beside it, is pv-msw8.

**8. The widget's persisted `view` field means "starting view". The identifier is a bounded exception.** Once the public site and the widget shared a view switcher (`CalendarViewToolbar`), a visitor could change the view inside the widget. The owner-configured value stopped being "the widget's view" and became the view the widget *opens on*, which the visitor may leave. The meaning changed, and the name stays where renaming would cost more than it buys:

- **Keeps `view`:** the `view` column on the stored widget config, the widget config API body, `WIDGET_CONFIG_DEFAULTS.view`, the admin form (`widget-config.vue`), the `view` parameter the admin preview puts on the widget iframe URL, and `view` in the SDK's `DEPRECATED_CONFIG_KEYS` (a legacy init argument the SDK warns about and ignores). Renaming the column, the API field or the preview parameter would be a migration or a wire change with no behavioural gain.
- **Reads the meaning, not the name:** TypeScript inside the widget calls the value `configuredView` (`src/widget/stores/widgetStore.ts`), and the view-state code calls it `defaultView` (`useCalendarViewState`, and the `defaultView` parameter of `calendarViewQuery` / `parseCalendarViewQuery`). New code that reads the stored field follows the TypeScript names.
- **The type is not widget-specific:** `CalendarViewMode` in `src/common/model/calendar_view.ts` is the single declaration of the allowed modes, shared by site, widget and server. It replaced the earlier `WidgetView`.

This follows the compensating-control pattern in [DEC-015 (federated report routing)](dec-015-federated-report-routing.md) (a name that no longer describes the behaviour is kept, and the decision file is where a reader of the name lands) and the bounded identifier exceptions in [DEC-007](dec-007-community-funding-model.md). The exception covers exactly the identifiers listed above. It does not license a new identifier that calls the starting view `view`.

**9. The view-state query vocabulary lives in `src/common/routing/calendar-view-query.ts`.** This module is not part of `src/common/ui`. It is URL vocabulary with no Vue in it, read by the site's calendar page and list filter, the widget's store and container, the client's admin widget preview, and the shared view-state composables, so it sits with the other routing modules. It is the single declaration of the `view` and `date` query keys and of when each one appears: `view` is present only when it differs from the surface's default, and `date` is present only for `week` and `month`. It also names the list filter's `startDate` / `endDate` keys, because the precedence rule between the two vocabularies has to refer to them. Its scope is **view-state vocabulary**, not the public calendar page's whole query contract: the same URL also carries `search` and `categories`, which `search-filter-public.vue` still spells as literals. Nobody should read this module as declaring those. It is the third module in `src/common/routing/`, next to [DEC-018](dec-018-root-calendar-urls.md)'s two. `reserved-segments.ts` says what a calendar may not be *named*, `public-paths.ts` says what a link to a page *looks like*, and `calendar-view-query.ts` says what a link to a *state* of that page carries. It stays outside DEC-018's builder surface and outside `public-url-contract.test.ts`, because it builds no path.

On the widget URL, `view` carries two meanings, and the module documents both. One is the visitor's deviation from the default, written only through `calendarViewQuery`. The other is the owner's configured starting view, which the admin preview always writes and the widget store's `parseConfig` reads once at load from `window.location.search`. The admin preview is the one sanctioned writer that skips default-omission, because it states a default rather than deviating from one. The meanings can share a key only because of an ordering invariant: configuration is read once, before anything writes the route, and never re-read after a `router.replace`. Reloading a URL that carries a visitor's `view` is a fresh load, so `parseConfig` treats that view as the starting view. That consequence is accepted. The SDK never puts `view` on the iframe URL, so only a visitor who switched views inside the frame and then reloaded it meets it.

**10. A value that varies by theme or by host is a runtime token. A value that does not is a compile-time constant.** Colour, shadow, `color-scheme` and the few non-colour values that differ by theme (`--pav-popover-backdrop-filter`, `--pav-vignette-gain`) are `--pav-*` custom properties. In the site and widget, every one of them is declared in one place: the `public-theme-tokens` mixin. Its base block holds the light values. Its private `_public-theme-dark-values` helper holds each dark value once, and the mixin includes that helper under both dark branches, the same dual selector the client's theme layer uses. The mixin is included only on `#app` in the site and on `.widget-root` in the widget. Because `color-scheme` comes from the same place, native controls inside the app switch with the colours around them. Spacing, type, radius, motion and breakpoints vary by neither theme nor host, so they stay `$public-*` Sass constants in `assets/mixins.scss` (rule 7). This rule is reopened by any owner-configurable non-colour value, such as a font or a radius chosen per calendar. A value compiled into the CSS cannot follow a host's choice. That is the bug class of pv-nskn, where the widget list view rendered the compiled default accent instead of the owner's, and such a value has to become a runtime token.

`scripts/check-theme-tokens.ts` enforces the rule. It runs in `npm run lint` and in the CI lint workflow, and it scans the style of `src/site`, `src/widget` and `src/common/ui`. It reports any `$public-*` family outside a closed non-colour allowlist. Outside the two token-layer mixins, it reports a `[data-theme]` selector, a `prefers-color-scheme` query, a `color-scheme` declaration, `light-dark(` and the retired widget theme classes. It also reports an include of `public-theme-tokens` anywhere but its two sites, and a misspelt `--pav-` prefix. There is no suppression comment. The only exemptions are the token-layer mixin bodies and the two include sites, each keyed on its file and its name. This is the first rule of this decision that binds code outside `src/common/ui`. Its residuals are recorded under rule 5.

## Context

The week and month views were built for the widget first. When the public site gained the same views, they had to live somewhere both apps could import. The tree then had no frontend-internal boundary at all. [DEC-003](dec-003-domain-driven-architecture.md) governs the backend domain split only. The widget already imported freely from `src/site` (components, stores, the `system` locale bundle), and the site imported from `src/client`. Putting the views in `src/site` would have extended that pattern. Building them twice would have meant two grids drifting apart.

The module shipped ahead of this record. `README.md`, `boundary.test.ts`, `breakpoints.test.ts`, the mixin and composable moves (each old path left as a shim) and the `ui` namespace came first. The styling contract was then rewritten from a `$public-*` stance, with the client excluded, to the current token-only stance, with the client as a consumer. So this file describes decisions already in code and does not choose new ones. The one rule it adds rather than records is the bundle-location rule in rule 6, for when a second feature needs `ui` keys.

The token-only stance covered shared components first. The site's and widget's own components still kept a compile-time palette: colour and shadow `$public-*` variables; a `public-dark-mode` mixin that wrote a separate dark block at every call site, 82 of them across 13 site files; seven raw `prefers-color-scheme` blocks in the site stylesheet; and a `color-scheme` block of the widget's own. Every dark block was another declaration site, which the widget's forced colour mode could miss and which a new component could forget. That palette was then retired. Every theme-varying value became a `--pav-*` token declared once in the token layer, the token layer took over `color-scheme`, `public-dark-mode`, its no-op `public-light-mode-override` twin and the site's `@forward` shim were deleted, and a lint guard keeps the tree in that shape (rule 10). Retiring the non-colour `$public-*` constants as well was considered and declined, which is why rule 7 calls `mixins.scss` a permanent home rather than a legacy one. The two-tier TOKENS.md (rule 4) came with that work too. The site and widget needed tokens the client has no use for, such as the date picker's chrome, and a shared component must still never read those.

Today the site's `src/site/components/calendar.vue` and the widget's `src/widget/components/widget-container.vue` both compose the shared calendar views: toolbar, `WeekView` and `MonthView`. The container wiring around those views lives in `src/common/ui/calendar-views/useCalendarViewContainer.ts`, which composes `useCalendarViewState` and `useCalendarWindowSync`, and both containers call it. It reaches the app store only through a structurally typed target, so it stays inside the boundary. Each container passes its default view, its events source as the `target`, a readiness check, a loading check, its locale and its route builders. Only the default view and the route builders differ between the site and the widget today. The readiness and loading checks are identical in both containers, because both mount `publicCalendarStore`. They stay with the caller deliberately: they read a store shape that the composable must not know under the structural-target design.

## Alternatives Considered

- **Status quo: the widget imports from the site.** The widget would keep reaching into `src/site` for the calendar views, as it already did for other things. Rejected because that makes the site the owner of components it doesn't own in any meaningful sense. A site-only change (a store import, a site mixin) would compile in the site and break only when the widget loaded the component, which nothing checks. It also leaves no place for the client to consume the same component.
- **`src/shared/`.** A new top-level directory beside `src/common`. Rejected because `src/common` already means "imported by more than one side". A second directory with the same meaning would force every future file to choose between two homes on no principle. The cost was a new property inside `src/common`, a browser-only part, and rule 2 names that cost and enforces it.
- **Migrate everything at once.** Move every site and widget component, composable and stylesheet that the other app touches into the new module in one change, and clear the widget → site imports with it. Rejected because the work is large, mostly mechanical and unrelated to the views that motivated the module. The module was scoped to what more than one app actually needs, with shims at the old paths, and the remaining cross-app imports were left as named, tracked debt.
- **`public-ui`.** Name the module after the two public apps and exclude the client. This was close to the original stance, when shared components compiled against `$public-*` values that only the site and widget could render. Rejected once the styling contract moved to runtime tokens. With every app declaring the recorded `--pav-*` names, nothing restricts a shared component to the public apps, and a name claiming otherwise would mislead.
- **Runtime spacing and type tokens for the site and widget (`--pav-space-*`, `--pav-font-size-*`).** This would retire every `$public-*` constant and leave the site and widget with no compile-time values at all. It was rejected for two reasons. First, those values vary by neither theme nor host, so a runtime lookup buys nothing (rule 10). Second, the names are taken. The client already declares `--pav-space-*` and `--pav-font-size-*` with different values: `--pav-font-size-sm` is 16px there and 13px here. Declaring them on the public side would make the type scale a shared name with diverging values, which is a convergence question for pv-olnr, not a side effect of a colour migration.
- **Plain `rem` values.** Convert the constants to literals, as shared components already write spacing and type. Rejected because it loses the named scale. `$public-space-md` says which step of the scale a value is, and a bare `0.75rem` does not.

## Rationale

The boundary exists because a violating import is invisible to the app that owns its target. A component that reaches into `@/site/stores` compiles and runs in the site and fails only when the widget or client mounts it. The allowlist turns that latent break into a test failure at the point of the import.

The token-only styling stance is what makes "shared" literal. A component compiled once against build-time `$public-*` values renders one palette everywhere. A component that reads runtime custom properties renders in each mounting app's theme, dark mode included, with no per-app variant. The accent rule (rule 5) follows from the one token whose value the module can't predict, because an owner chooses it.

Rule 10 puts the line between runtime and compile-time where a value's source of truth sits. A value that can change after the CSS is built, through the OS preference, the widget's forced colour mode or an owner's setting, has to be resolved in the browser. Declaring it in one place is what stops a forced mode from missing a branch. A value that never changes gains nothing from a lookup and keeps the readability of a named Sass scale.

Component-owned translation keys follow from the same reasoning as the import boundary. If an app supplied a shared component's copy, the component's text would depend on which app mounted it, and each app would need to know its dependencies' internals.

Rule 8 keeps the stored and wire names because renaming them buys nothing a reader can't get from this file and the TypeScript names. Recording the exception keeps the old name from spreading into new code.

## Consequences

- **This is the first frontend-internal boundary.** [DEC-003](dec-003-domain-driven-architecture.md) governs backend domains. Before this, no rule governed which frontend app may import from which. `boundary.test.ts` enforces the import boundary, and its scope is this module only. The theme guard (rule 10) is the first enforcement of this decision that binds code outside it, in the site's and widget's own style. The guard is canonical tree-wide. `boundary.test.ts` keeps its tighter checks on shared components (no `$public-*` of any family, shared-tier names only, layout-only mixins, no theme selector) because they run under `npm test` with a module-specific message. Where both fire, both are right.
- **Existing cross-app imports are tracked debt, not violations.** The widget → site and site → client runtime imports elsewhere in the tree are tracked on pv-ese5. (They were first tracked on pv-z1in, now closed. `src/common/ui/README.md` and `boundary.test.ts` cite pv-ese5.) One of them survives this work by design: the widget's `system` namespace, which `src/widget/service/locale.ts` imports from `src/site/locales/`. That is app-level copy, outside rule 6, so the widget keeps reading the site's `system` bundle even though `ui` exists. Removing it means giving the widget its own app namespace, not moving it into `ui`.
- **No client styling reaches a public render.** No `@/client` module reachable from the site or widget carries a stylesheet, a dark selector or a client-only token. The remaining imports are services, a store and the logo SVG used as a CSS mask, and they are tracked as boundary debt on pv-ese5. The check was made when the public palette was retired. A future import of a client `.vue` or `.scss` file into the site or widget would bring the client's own `[data-theme]` rules with it and break rule 10, which the guard would not see, because it does not scan `src/client`.
- **The styling contract constrains token work.** Any change to the token set goes through TOKENS.md. A shared token goes into both apps' token layers, and a public-only one goes into `public-theme-tokens` alone, named so that it collides with no client name. `public-theme-tokens.test.ts` holds them together. Promoting a public-only token to shared means declaring it in the client's theme layer first. Spacing and type sizes have no runtime token (rule 10), so shared components write them as plain `rem`. Palette convergence (pv-olnr) and the accent text pair (pv-8l49) are open, and either one changes rule 4 or rule 5 in place.
- **Colocated tests are a property of this module, not a new `src/common` convention.** This module's tests live under `src/common/ui/test/`, mirroring its layout, so the module moves as one piece. Elsewhere in `src/common` an area's tests stay under `src/common/test/<area>/`. `calendar-view-query.ts` is tested at `src/common/test/routing/` for that reason.
- **The boundary scan is textual.** A quoted import specifier inside a comment under `src/common/ui` counts as an import. That is deliberate, so a comment can't hide a real import, but it means documentation examples are written without quotes. pv-e62b would move the scan to the AST.
- **The widget's starting-view naming is permanent until a rename is worth a migration.** Readers of the column, API field or preview parameter land here through the index's Consult-when list.
