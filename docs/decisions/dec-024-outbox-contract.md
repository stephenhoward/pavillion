# DEC-024: The Outbox Contract

> Date: 2026-11-09
> Status: Accepted
> Category: Technical
> Stakeholders: Tech Lead, Calendar Owners

## Decision

`ap_outbox` holds one row per activity a local calendar's outbox sends, written only by `addToOutbox` (`src/server/activitypub/helper/outbox.ts`). A calendar's **public outbox** — the collection `readOutbox` serves anonymously at `/calendars/:urlname/outbox` — is a subset of those rows, chosen by a stored membership flag and by whether processing succeeded, never by how delivery went.

**1. Membership of a new row.** `is_public` is true when the activity's `actor` equals the anchoring calendar's actor URL (`ActivityPubActor.actorUrl`) **and** its `to` or `cc` names `as:Public` or `${actor}/followers`. A row with no addressing is not public. `isPublicOutboxActivity` decides this once, at insert.

**2. Membership of a row stored before the column existed.** Migration `0050_add_ap_outbox_is_public` backfilled `is_public` with a frozen copy of the rule, `backfillIsPublic`, which differs from rule 1 in two ways: the actor is compared by **path** (`/calendars/<url_name>` of the row's calendar), so a changed instance domain keeps its history; and a row whose `to`, `cc`, `bto`, `bcc` and `audience` are all empty (absent, null, `[]` or `''`) is public, because activities written before public addressing was added on 2026-04-30 carry none and they are the calendar's oldest originals. That clause is **history only** — it never applies to a new row. Before `toObject` began writing `to`/`cc` (commit e382b38f, 2026-01-04), every calendar-actor row was stored with no addressing, so the backfill also set `is_public` true on old Follow, Accept, Flag, Undo, Add and Remove rows. Anything malformed is not public. The actor is parsed with `URL`, never matched as a substring.

**3. What `readOutbox` serves.** Rows of a public type (`Create`, `Announce`, `Update`, `Delete`) where `is_public` is true, `processed_time` is set, and `processed_status` neither starts with `error:` nor equals `bad message type`, minus any Announce with a recorded Undo. `error:` means processing threw and `bad message type` means the type is unknown: neither was published. `partial:` and `skipped:` are **delivery outcomes** and do not affect membership — a public Create whose delivery to one follower failed is still the calendar's public activity, and a Create the drain skipped as `skipped: superseded` (rule 10) is still one the calendar published, served beside the Delete that retracted it. An unprocessed row has not been validated yet. Every writer sets `processed_status` together with `processed_time`, so a processed row with no status does not occur. The page and its `totalItems` count read the same filter.

**4. `is_public` is a third class of denormalized column** beside the two in [DEC-015 (activity-log routing keys)](dec-015-activity-log-routing-keys.md): a **write-once derived fact of the row's own content**. It is neither a display snapshot nor a routing key. Its source, `message`, is write-once; `is_public` is written only at insert and by migration; a change to the rule is a new backfill migration, never an edit to an existing one; it is read only by `readOutbox`; and it never answers "is this activity visible now". It **is** an input to one gate, the anonymous-serving filter in `readOutbox` (rule 3). That is permitted because it is a write-once fact derived from the row's own content, not a copy of another table's live state, which is what DEC-015's rule 2 guards against. Rule 2 still forbids it deciding anything outside `readOutbox`.

**5. Comparing a row's actor is not the identity re-derivation [DEC-013](dec-013-inbox-authenticated-activity-log.md) forbids.** That ban governs inbound gates, where `actor` is a peer's self-assertion. Outbox rows are produced locally by our own code, so their `actor` is a fact we wrote.

**6. Followers-only rows are public.** A calendar's followers are an audience of a public actor, not a confidentiality boundary: anyone can follow.

**7. Nothing is deleted.** Rows that are not public — chiefly a local editor's Update or Delete on a remote calendar, signed by the user actor and anchored on a local calendar's outbox — stay in `ap_outbox`, unserved (retention is pv-crcp). The filter closes **pull** exposure only: the remote calendar still receives the editor's actor URI by POST, and peers keep any copies they took from the outbox before this change.

**8. Rules that must be re-read together.** A feature that renames a calendar (`setUrlName`, [DEC-018](dec-018-root-calendar-urls.md) rule 4) changes the actor URL rule 1 compares against while stored rows keep the old one, so it must revisit membership. Widening the type filter (pv-owy4, e.g. serving Undo) must re-read rule 3. `is_public` on a row of a type outside the served list is not evidence that it is public (rule 2 set it on unaddressed Follow, Flag and Undo rows), so widening must re-derive membership for the added types, not trust the stored flag. A new reader of `ap_outbox` that serves anything anonymously must apply rule 3, not re-derive it. A new `processed_status` value must be placed in rule 3 (served or not) and in the operator guide.

**9. The outbox drain.** Every row is delivered first by the live `outboxMessageAdded` handler. A row whose emit went to a process that stopped before handling it is delivered by the web process's drain, `ActivityPubDomain.startOutboxDrain`. At boot, not awaited so it never holds up `listen` or `/health`, it takes every unprocessed non-superseded row whose `message_time` is at or before the moment the drain starts (`skipNewerThanMs: 0`; the cutoff is fixed once per drain, and a row written in the same millisecond still qualifies). Every row a restart stranded predates boot, so the cutoff loses none of them, and a row written after it belongs to its live handler: without the cutoff, the boot drain on PostgreSQL would keep re-querying into rows still in live delivery, delivering them twice, and under sustained writes might never finish, leaving every later tick a no-op. Then every 60 seconds (`activitypub.outboxDrain.intervalMs`; e2e and federation set 5 seconds) a tick takes rows at least 15 minutes old (`OUTBOX_DRAIN_SKIP_NEWER_THAN_MS`). The window is 15 minutes, not the inbox's 10 seconds, because each recipient can cost two HTTP timeouts and one fan-out with a dead peer routinely outlasts 10 seconds; every row has a live handler, so no row waits on a tick to be delivered. The interval is a latency choice; the window is the correctness choice. Both cutoffs are measured on `message_time`, unlike the inbox's `createdAt`, because an outbox row's `message_time` is our own clock at write and is the column `idx_ap_outbox_unprocessed` (migration 0051) orders by. A tick that finds a drain in flight starts nothing. A row that throws is marked `error:` through `markOutboxMessageFailed`, the one bounded write the live handler shares, and the drain moves on; if even the constant fallback `error: processing failed` cannot be written, the drain rejects rather than re-reading the same row forever, and the next tick runs. The live handler skips a row that already has `processed_time`. A local dispatch refused because the activity id is off our origin ends the row `error:`, not `partial:`: a broken own-origin invariant is unserved, never a delivery note. The inbox boot drain ([DEC-013](dec-013-inbox-authenticated-activity-log.md)) has the same uncut shape, with smaller exposure because live inbox dispatch is short; giving it a cutoff is out of scope here and tracked as follow-up pv-ytt8.

**10. Supersession, drain path only.** Before delivering a Create, Update or Announce, the drain checks `ap_outbox` for a `Delete` with id `{objectId}/delete` (the id `DeleteActivity` gives a Delete of that object, whether the row's `object` is a string or carries an `id`) or an `Undo` with id `{rowId}/undo` (the id `UndoActivity` gives an Undo of the row). Type and id are both matched, as `readOutbox`'s Undo probe does. If either exists the row is marked `skipped: superseded` and not delivered; the retraction itself is delivered as usual. The live handler does not check: it runs before anything can retract the row. Changing the id `DeleteActivity` or `UndoActivity` mints breaks this rule. Two gaps are accepted. Two stranded Updates of one object are both delivered, oldest first, so a peer briefly sees the stale one. And [DEC-008](dec-008-unpost-dismissals.md)'s unpost emits only `Undo(Announce)`, never a Delete of the paired repost `Create(Note)`, so supersession cannot see that the Note was taken back: a stranded Note is delivered by the drain even after an explicit unpost, which is worse than the live path, where the Note went out before the unpost and simply stays unretracted. Follow-up pv-bvh2 tracks both halves.

**11. Delivery is at-least-once.** A row a restart cut off mid-fan-out is redelivered from its first recipient. No row is claimed: on PostgreSQL a tick and the live handler can still deliver one row twice when a live delivery outlasts the 15-minute window, and the boot drain can take a row whose live handler was mid-flight when the process started serving. That peers deduplicate on activity id is unverified beyond our own HTTP path. Local dispatch runs at most once per (activity, recipient) for **repeated** dispatch, not for **concurrent** dispatch, and only because every locally dispatched activity id is on the instance domain. Both drains assume one web process: a second replica needs a claim for the inbox and the outbox drain alike before it can scale out, tracked as follow-up pv-rbyk.

**12. Web process only.** A drain runs local dispatch (`dispatchByType`), which needs every domain's event handlers. `server.ts` starts it after every domain has initialized and stops it in both shutdown paths; stopping clears the interval only, and an unfinished row is redelivered on the next boot. The worker holds an `ActivityPubInterface` without those handlers and must never call `processOutboxMessages`.

**13. What a drained row still reaches.** Recipients come from `getRecipients` at send time, so a follower that left is not reached. There is no outbound instance-block check on live delivery, and a drained row behaves the same: redelivery can reach an instance blocked after the row was written. A slow or dead inbox costs up to recipients × timeout inside the drain, which delays the rows behind it but never stops them.

## Context

The public outbox used to serve every public-type row whose `processed_status` was exactly `'ok'`. Two defects followed. A public activity whose delivery to one unreachable follower failed ended `partial:` and vanished from the outbox, so a new follower's backfill walk never saw it. And the filter did not look at who the activity was from: `FederationPublisher` anchors a local editor's Update to a remote calendar on a local calendar's outbox, signed by the editor's user actor and addressed only to that remote calendar, and the public outbox served it to anyone — disclosing the editor's actor URI.

Delivery itself had a third defect. A row was delivered only by the `outboxMessageAdded` emit that followed its write, so a row whose emit went to a process that stopped, crashed or was redeployed before handling it stayed unprocessed forever, and one recipient whose actor fetch threw ended delivery for the recipients behind it. Rules 9 to 13 record the drain that now picks those rows up and the limits accepted with it.

## Alternatives Considered

1. **Filter at query time on the stored JSON.** Rejected: the rule needs JSON predicates on the actor and the addressing fields that differ between SQLite and PostgreSQL, and filtering on them would stop the page query being a backward scan of `idx_ap_outbox_calendar_message_time`.
2. **Mark rows with no addressing as not public in the backfill too.** Rejected by ruling: it would remove every calendar's oldest originals from its outbox.
3. **Purge the stored user-actor rows.** Rejected by ruling: an open retention question, and a destructive migration.
4. **Compare the actor with the calendar's current actor URL in the backfill.** Rejected: a changed instance domain would drop a calendar's whole history.
5. **Claim a row before delivering it.** Rejected for now: the deployment is single-replica, the 15-minute window makes the live/drain overlap rare, and a claim belongs with the inbox's (both drains need one before a second replica).
6. **Check supersession on the live path too.** Rejected: a live row is delivered as it is written, before a retraction can exist, so the check would only add a query to every delivery.

## Rationale

A stored flag keeps the page query on its index (the filter columns are checked on the heap rows the index returns) and makes the rule something a test can pin on both dialects. Deciding membership from the activity's own actor and addressing, rather than from delivery status, makes the outbox say what the calendar published, which is what followers' backfill walks and FEP-8a8e consumers ([DEC-014](dec-014-create-original-announce-repost.md)) read it for. Keeping the backfill's extra clause out of the live rule means an unaddressed activity written from now on is a bug that stays private, not one that is published.

## Consequences

**Positive:**
- A public activity stays in the outbox whatever its delivery outcome, and `totalItems` agrees with the pages.
- User-actor activities anchored on a calendar's outbox are no longer served anonymously.
- The page query still uses `idx_ap_outbox_calendar_message_time`.

- A row a restart stranded is delivered at the next boot, unless a later Delete or Undo already retracted it.
- One row that throws, or one dead peer, no longer stops the rows behind it.

**Negative:**
- Membership is frozen per row. A rule change, or a calendar rename, needs a backfill migration to reach stored rows.
- Two copies of the rule exist, the live one and the migration's frozen one; a shared case table (`src/server/activitypub/test/helper/public-outbox-activity.test.ts`) pins where they agree and labels the two places they differ.
- Exposure that already happened is not undone: peers that walked an outbox before this change keep the user-actor activities they took.
- Delivery is at-least-once, and the first boot after this change delivers everything stranded since the outbox began; operators can count those rows first (see the monitoring guide).
- A second web replica would double-deliver until both drains take a claim.
